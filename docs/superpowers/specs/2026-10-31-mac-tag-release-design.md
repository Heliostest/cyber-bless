## 发布顺序

1. 确定本次版本和构建号，核对 ASC/EAS 已用号并串行处理；把非敏感的版本、构建号、应用身份和工具链要求保存为 Git 跟踪的发布输入。机器路径与签名秘密不进入 Git。
2. 完成业务改动、发布脚本、依赖锁和上述发布输入的审阅、提交，合并至 `master`；在合并后的准确提交运行规定检查。失败必须报告，不把旧失败自动豁免或宣称全绿。检查后若再改任一输入，重新提交并验证。
3. 推送发布提交和 LFS 对象，再创建并推送附注 tag，例如 `ios/v1.0.0-build.19`。这只是命名示例，不分配或创建下一个实际构建号。
4. 获取入口检查 tag 已在 `origin`，其提交已包含在远端 `master` 历史中，解析并固定完整 tag 对象、commit 与 tree ID。后续 `master` 前进不影响旧 tag 重建。禁止覆盖已存在的发布 tag。
5. Mac 获取准确 tag，创建独立 detached checkout，拉取并还原该提交需要的 LFS 实体；缺少对象、仍是指针或 SHA 不符即停止。
6. 从该 checkout 内的绝对路径执行 prepare、build、verify、upload 等发布脚本，核验身份和输入后按原有签名与 ASC/TestFlight 流程工作。
7. 保存小型发布记录：tag、对象/提交/tree ID、依赖和工具链、文件哈希、IPA 哈希、archive/dSYM 路径及上传结果。大型临时源码目录可在不再使用后清理，不再生成正式发布用的 `source.tgz`。

发布入口不执行笼统的 `git add .`、自动合并或提交开发目录。开发目录可以继续存在独立工作；任何未提交文件都不会混入已选 tag 的发布。创建新发布版本前必须审阅并提交该版本需要的改动。

## Mac 获取与目录边界

建议使用 `/Users/heli/ios-builds/cyber-bless/`，其下分开保存 Git 对象缓存、每次发布的源码、发布产物和可重建缓存。保持 App 专用目录，不覆盖旧构建副本或开发仓库。

获取用的小型启动入口只负责 Git/tag/LFS 获取与身份验证，不承担 prebuild、签名或上传。准备完成后启动 **该 tag 中的脚本**，避免让旧 prepare 进程一边运行一边被新源码覆盖。

- 首次补齐 Git LFS，只使用现有或明确配置的仓库访问能力，不把令牌写入 URL、配置回执或日志。
- 准确比较远端附注 tag 对象与解析后的 commit；不存在、发生移动或无法核验则失败，不回退到工作区快照。
- 获取源码时固定换行策略；安装依赖、生成原生工程前，检出目录必须干净。
- 正常重试可以复用已验证的同一 tag 检出和产物，不能重置含未知改动的目录。所有删除和移动都必须先验证绝对路径属于本项目专用构建根目录；不跟随 junction 或 symlink 删除其目标。
- 同一 App 的版本检查、准备、构建、签名和上传使用独占锁。查询编号不等于预留编号，归档和上传前仍检查冲突。

## 输入与脚本核验

复用现有逐文件 SHA-256 manifest，增加 tag、tag 对象、commit/tree、来源模式和依赖/工具链身份。Git 模式不再用 `sourceCommit` 加任意归档哈希代表源码真实性。

- `scripts/ios-release/` 全部正式入口及其本地依赖必须被 tag 跟踪，并列入核验范围。
- 各入口验证自己实际位于配置指向的发布 checkout，脚本哈希与固定 manifest 一致；不同版本的准备、构建、验证和上传回执不能混用。
- 构建前重验输入；允许的生成变化沿用当前明确的 prebuild 白名单，不笼统放行所有改动。`source-post-prebuild.json` 必须成为构建入口的有效前置证据。
- 上传前再次核验固定输入、验证器、IPA 与本轮验证回执，不能只依赖先前生成的成功 JSON。
- 冻结后若需修改业务或发布脚本，必须提交并使用新 tag。已构建的 IPA 保持原记录，不用新脚本版本覆盖旧身份。
- 既有源包模式回执按历史 schema 解释；新正式发布不允许退回脏工作区源包。构建 18 等旧记录保持历史事实。

## 依赖与工具链

`package-lock.json` 已跟踪。新发布 checkout 使用 `npm ci`，共享下载缓存，不直接继承旧目录的 `node_modules`。记录并检查实际 Node/npm、Ruby/CocoaPods、Xcode 版本与 build number、SDK 以及必要平台信息，不使用写死的报告文字冒充实际探测结果。

当前原生目录整体忽略，尚无 Git 跟踪的 Podfile.lock/Gemfile.lock。为避免 tag 相同而原生依赖变化，应把发布用 CocoaPods 锁文件作为单独跟踪的输入，prebuild 后使用该锁执行 deployment 安装；从经核验的成功构建取得初始锁并在 tag 前提交，不擅自升级现有依赖。工具链沿用项目已验证的版本，实际可用性在执行时核对。

DerivedData 等缓存按工具链和依赖身份隔离并加锁，缓存不参与源码身份。tag 固定源码和脚本，依赖锁与工具链约束支持重复构建；不承诺重新签名后 IPA 字节完全相同。
